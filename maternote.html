Deployment Notes

Production deploy currently uses the repo at /opt/scion. The API listens on 127.0.0.1:8000 and the web server listens on 127.0.0.1:3000. The successful post-deploy readiness response was: 

{"status":"ready","dataset_records":118,"applied_migrations":6}

Important operational lesson: scripts/stop_stack.sh only stops processes it knows through the stack PID files. A stale unmanaged next-server from May 19 stayed bound to port 3000 and caused the public site to serve the old build. If production looks stale, inspect the actual process bound to the port. 

WEB_PID=$(ss -ltnp 'sport = :3000' | sed -n 's/.*pid=\([0-9]*\).*/\1/p' | head -1)
ps -fp "$WEB_PID"
readlink -f /proc/$WEB_PID/cwd

If a stale web process is serving the old build, kill it, clean-build, and restart: 

cd /opt/scion
kill "$WEB_PID"
rm -rf apps/web/.next
make web-build
scripts/start_stack.sh

Confirm both local and public routes after deployment: 

curl -fsS http://127.0.0.1:3000/ | grep -o 'CAOS' | head
curl -fsS http://127.0.0.1:3000/caos | grep -o 'CAOS' | head
curl -fsS http://127.0.0.1:8000/api/health/ready
curl -fsS https://cellanatomy.org/ | grep -o 'CAOS' | head
curl -fsS https://cellanatomy.org/caos | grep -o 'CAOS' | head

CAOS Full Operating System Vision

This section is intentionally expansive. These are internal product directions and moonshot ideas, not public commitments. Keep them here so the team can see the full possible arc while deciding what is actually worth building.

Core Operating System Shape

  • Atlas layer: public field map for literature, datasets, modalities, reporting completeness, precedent, and gaps.
  • Workbench layer: local/native environment for opening user data, inspecting volumes, measuring structures, defining ROIs, and running jobs.
  • Project layer: persistent project files that contain datasets, views, measurements, notes, ROIs, jobs, exports, and provenance.
  • Analysis layer: calibrated tools for measurements, segmentation-adjacent workflows, quality checks, density/intensity summaries, and reusable exports.
  • Publication layer: clean outputs for figures, methods tables, provenance reports, CSV/JSON bundles, and eventually manuscript-support packages.

Idea To Publication Flow

  • Start with a biological question or target structure.
  • Use the Atlas to find precedent, comparable datasets, common resolutions, reporting norms, and field gaps.
  • Open public or local data in the Workbench.
  • Create calibrated measurements, ROIs, notes, and view states tied to exact volume coordinates.
  • Run local jobs for indexing, summaries, previews, exports, and later analysis modules.
  • Bundle the work into shareable project artifacts with provenance, figures, and machine-readable outputs.
  • Use the final bundle to support papers, grant planning, reviews, internal reports, or reproducibility packages.

Near-Term OS Features

  • Project save/load that restores dataset, asset, view mode, slice position, contrast, colormap, measurements, ROIs, notes, and jobs.
  • Local folder indexing with clear queue states, retries, failure explanations, and validated metadata summaries.
  • Measurement and ROI exports that are useful outside the app without manual cleanup.
  • Atlas-to-Workbench handoff: public record opens relevant local/public volume context when available.
  • Workbench-to-Atlas handoff: local observations can be used to update planning or comparison context.
  • Better density preview with a real purpose: structure finding, intensity summary, segmentation planning, or quality assessment.
  • Native macOS packaging as a downloadable .dmg.

Medium-Term OS Features

  • Project dashboard with recent volumes, pinned views, measurements, notes, and unfinished jobs.
  • Annotation system for structure labels, hypotheses, uncertainty, and review comments.
  • Versioned project history so users can recover or compare analysis states.
  • Plugin-like job modules for common workflows: downsampling, preview generation, measurements, masks, simple segmentation helpers, and figure exports.
  • Cross-volume comparison: align measurements and regions across related samples or conditions.
  • Validated data-readiness checks for dimensions, voxel size, dtype, missing chunks, metadata conflicts, and licensing notes.
  • Figure builder for reproducible panels: view state, scale bar, labels, contrast, colormap, and source metadata captured together.

Moonshot Ideas

  • Cell anatomy notebook: a structured notebook where every claim is linked to volume coordinates, measurements, and source records.
  • Autonomous literature-to-data scout: propose datasets, methods, and precedent from a research question, then create a Workbench project shell.
  • Atlas-guided experiment planner: recommend resolution, sample count, modality, and reporting checklist based on field precedent and gaps.
  • Collaborative review mode: multiple reviewers comment on the same regions, measurements, and figure states.
  • Model-assisted structure finding: use learned or rule-based tools to suggest organelles, membranes, unusual regions, or likely artifacts.
  • Reproducibility package generator: produce a methods appendix, data citation block, figure provenance, and machine-readable measurement archive.
  • Protocol marketplace/library: reusable analysis recipes for specific modalities, organisms, organelles, and publication goals.
  • Cloud-assisted optional compute: local-first by default, with optional remote jobs for heavy processing when compliance and cost are solved.
  • GitHub-connected science workflow: export versioned project artifacts, issues, and provenance bundles into a repository for labs that work that way.
  • Cell anatomy benchmark suite: standardized public tasks for comparing imaging workflows, segmentation tools, and measurement reproducibility.

Product Boundaries To Keep Asking

  • Who actually needs this?
  • What job does it do better than existing tools?
  • Does it move a user from idea to execution to publication?
  • Does it produce a reusable artifact, or just a neat visualization?
  • Can we explain the feature without pretending it is more complete than it is?
  • Can it work locally and privately before we ask users to trust cloud/account infrastructure?

Ideas Parking Lot

  • Dataset citation manager for volume projects.
  • Field-gap alerts when new public data appears in a target area.
  • Lab-local template projects for repeated organisms, modalities, or structures.
  • Review checklist for public-data readiness and metadata completeness.
  • Exportable “methods card” summarizing imaging, voxel size, sample count, processing, and measurement choices.
  • Interactive cell anatomy atlas view that links literature records to example volume slices.
  • Account-backed project sync only after local-first workflows are strong enough to justify it.

Email And Account Infrastructure

Current local account testing does not send real email. Login codes are written to apps/api/.run/auth-codes.log. The configured placeholder sender is Cell Anatomy <no-reply@cell-anatomy.local>.

Production needs two related but separate pieces: human inboxes for the team and support flow, and a transactional sender for login codes.

Recommended Setup

Human Email

Use one normal mailbox provider for the two lead inboxes, plus aliases or groups that forward into those inboxes. Google Workspace is the default recommendation if the leads already use Gmail. Fastmail is a reasonable cheaper option. 

lead1@cellanatomy.org
lead2@cellanatomy.org

hello@cellanatomy.org      -> both leads
feedback@cellanatomy.org   -> both leads
support@cellanatomy.org    -> both leads
accounts@cellanatomy.org   -> both leads or admin
security@cellanatomy.org   -> owner/admin + technical lead
privacy@cellanatomy.org    -> owner/admin + technical lead

Transactional Email

Use a transactional provider for login codes instead of sending from a personal or shared inbox. Start with Resend for cost and simplicity; consider Postmark later if deliverability becomes the main concern. 

SCION_AUTH_EMAIL_FROM="Cell Anatomy <accounts@cellanatomy.org>"
SCION_AUTH_SMTP_HOST=smtp.provider.com
SCION_AUTH_SMTP_PORT=587
SCION_AUTH_SMTP_USERNAME=...
SCION_AUTH_SMTP_PASSWORD=...
SCION_AUTH_SMTP_STARTTLS=true

Estimated Cost

  • Domain: roughly $10-20/year if we do not already own the final domain.
  • Google Workspace: about $14-17/month for two users, depending on annual versus monthly billing.
  • Fastmail alternative: about $10-12/month for two users.
  • Resend transactional email: free at first if traffic stays within the free tier; about $20/month later.
  • Postmark transactional email alternative: about $15/month starting tier.

Practical starting budget: about $14-17/month plus the domain. If/when paid transactional email is needed, expect about $34-37/month plus the domain.

DNS Requirements

The domain needs standard email authentication so Gmail, Outlook, and other receivers trust account emails.

  • MX: routes human inbox mail to the mailbox provider.
  • SPF: authorizes the mailbox provider and transactional provider to send for the domain.
  • DKIM: cryptographic signing records from each provider.
  • DMARC: policy and reporting layer built on SPF/DKIM.

Needed From Leads

  • Final domain choice, for example cellanatomy.org or another approved domain.
  • Human mailbox provider choice: Google Workspace, Fastmail, Proton, or another provider.
  • The two lead inbox names.
  • Approval for aliases: hello@, feedback@, support@, accounts@, security@, privacy@.
  • Routing decision for each alias. Simple default: public/support aliases go to both leads; security/privacy go to owner/admin plus technical lead.
  • DNS access, or permission for the technical setup person to provide records that the domain owner adds.
  • Billing owner for Workspace/Fastmail and Resend/Postmark.

Product Implications

This keeps the account system simple while still giving us a credible path for user support, login-code delivery, feedback collection, privacy contact, and future GitHub/OAuth integrations if those become necessary later.

No triage system is needed now. A shared inbox or aliases funneling into two lead inboxes are enough until volume proves otherwise.
